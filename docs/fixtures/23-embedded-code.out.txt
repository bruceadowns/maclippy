Loren's framing is right, and the code says why in one line.

HistoryUtils.checkGeography looks up the collection before it ever looks at the predicate:

String geoField = GEO_FIELD_BY_COLLECTION.get(collectionName);
if (geoField == null) {
    return doc;            // untouched — the filter never runs
}

The predicate is evaluated on the next line, which those five collections never reach. So there is no per-predicate variation available to observe on them - all nine behave identically because none of them executes. "Negatives fail" is the symptom of an unreached branch, exactly as Loren put it.

The split he's pointing at is that validation and application are keyed on different things: validation on the parameter name (fires for all 66 history facades), application on the collection name (only the mapped ones). That is why a service can 400 a bad region and still ignore a good one.

His four filtering services are the mapped WKT collections - poi, sigact, weatherreport -> atext, groundimagery -> regionText. Three more filter and are probably not in the matrix: document, acled, cidne, all on a nested geoLocation document rather than a WKT string. Worth adding if the run is meant to be exhaustive, since they exercise a different read branch.

This is AFDL-66733, already written up. Not a defect in 66683 or 66686.

Two things worth confirming with QA before the matrix is trusted, because each produces the same "negatives fail" signature by a different mechanism:

Which endpoint did the matrix hit? /history/count ignores the region on every service, poi included (AFDL-66743). If any negatives ran against count, poi would also show failures and the per-service split would look inconsistent.

Which component-library version is deployed? Before AFDL-66686, equals_ matched zero records on history even on poi - positives fail, negatives pass, which reads as a per-predicate defect. If Loren's earlier per-predicate framing came from a poi/equals observation, a stale CL version explains it.
